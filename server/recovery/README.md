# Независимость от одного сервера

Первый этап — один активный PocketBase, выключенный резерв у другого провайдера
в России и зашифрованные копии у третьего поставщика/в отдельном аккаунте.
Несколько одновременно пишущих PocketBase с SQLite не используем.
Существующий прокси в Нидерландах не заменяет резерв базы.

## Что уже подготовлено, а что ещё предстоит

- `export-backup.sh`: проверяет свежесть штатного ZIP PocketBase, CRC архива и
  целостность SQLite, отправляет архив, код, бинарник с версией и конфигурацию
  в зашифрованный restic. Сервис не останавливает, живую базу не копирует.
- `pb_backup.py`: проверяет архив, восстанавливает только в НОВУЮ папку,
  не запускает PocketBase. Отсекает опасные пути, ссылки и SQLite sidecar-файлы.
- GitHub Actions: внешняя проверка обеих витрин и каталогов. Включается переменной
  репозитория `EXTERNAL_MONITOR_ENABLED=true`, либо вручную. Задания GitHub могут
  задерживаться; это дополнительная проверка из одной сети, не SLA-мониторинг.
  Уведомления о неуспешных заданиях нужно включить в личных настройках GitHub.

Эти файлы сами по себе НЕ создают VPS, хранилище, копии, расписание экспорта
или DNS-переключение. На реальной копии базы восстановление ещё не проверено.

## План внедрения

1. Уточнить доступ к Timeweb, наличие последнего ZIP и его фактическое содержимое.
   По миграции штатные копии создаются в 04:00, хранятся 14 штук; фактическую
   настройку и место хранения подтвердить на сервере. Объектное хранилище файлов,
   если включено в PocketBase, копировать отдельно: ZIP может не содержать эти фото.
2. Создать отдельное хранилище в России; настроить restic и проверить `restic check`.
   Пароль хранить вне сервера в менеджере паролей; без него восстановление невозможно.
   Учётные данные — root-only файл вне git, не в чате и не в GitHub-артефактах.
   Если настроено шифрование настроек PocketBase, отдельно сохранить исходный
   ключ/переменную среды из реальной службы. Без него интеграции не восстановятся.
3. Установить export-скрипт, Python и restic на основной сервер. Проверить пути
   Caddy, systemd unit, bin, hooks и migrations. Создать репозиторий restic один раз
   командой `restic init` с отдельными реквизитами. Скрипт намеренно не делает init.
   Запустить экспорт вручную с `RESTIC_REPOSITORY`, `RESTIC_PASSWORD_FILE` и
   реквизитами хранилища. Назначить расписание экспорта ПОСЛЕ создания штатного ZIP.
4. Провести учебное восстановление по инструкции ниже на выключенном резерве.
   Только после измерения времени восстановления назначать целевой срок.
5. Увеличить частоту штатных копий до часа после проверки нагрузки/размера;
   экспортировать каждую завершённую копию, `MAX_BACKUP_AGE_SECONDS=7200`.
   До этого возможная потеря данных — больше суток при ежедневных копиях;
   экспорт старого ZIP чаще не делает данные свежее. Будущая цель: потеря не более
   часа плюс задержка экспорта, восстановление за 30–60 минут после учений.
6. Независимый мониторинг из России и второй сети, отдельные оповещения о
   недоступности и отсутствии свежих копий. Проверять скачивание копий и
   `restic check --read-data-subset=10%`; полное восстановление — ежемесячно.
7. DNS держать доступным независимо от VPS; заранее снизить TTL A/AAAA до 300 с.
   Регистратор указан в проекте как reg.ru, фактические NS ещё проверить.
   DNS-переключение не мгновенно, старые соединения сохраняются.

## Учебное восстановление без отправки сообщений и списаний

1. Чистый резервный VPS: Ubuntu, архитектура как у исходного сервера, Caddy,
   системные зависимости из исходной службы. Пользователь `venikoff`.
   PocketBase НЕ запускать, в том числе для проверки версии на базе.
2. `restic snapshots --tag venikoff-recovery`; выбрать конкретный snapshot ID.
   `restic restore ID --target /srv/restore-ID`. В snapshot ZIP находится в корне,
   код/бинарник/конфигурация — в исходных абсолютных путях под целевой папкой.
3. `python3 server/recovery/pb_backup.py /srv/restore-ID/pocketbase.zip`
4. `python3 server/recovery/pb_backup.py /srv/restore-ID/pocketbase.zip --restore-to /srv/pb-data-ID`
   Родитель должен существовать, целевая папка — отсутствовать. Нужен свободный
   диск под snapshot, ZIP, распаковку и временную проверку базы.
5. Сверить SQLite, число/свежесть заказов и наличие фотографий БЕЗ запуска приложения.
   Зафиксировать дату копии, snapshot ID и время восстановления. Не публиковать
   клиентские данные/токены в отчётах. Проверка CRC/SQLite не доказывает полноту
   бизнес-данных и работоспособность интеграций.
6. Для полноценной проверки приложения нужен изолированный стенд без исходящих
   подключений и публичного входа: восстановленные hooks сами запускают фоновые
   задания. Даже запросы чтения могут запускать обработчики. Не включать службу
   на обычном сетевом стенде с боевыми ключами.

## Переключение при аварии — вручную

1. Сначала исключить работу прежнего сервера (выключение/сетевая изоляция в панели
   провайдера). Тайм-аут из одной сети этого НЕ доказывает. Если изоляцию нельзя
   подтвердить, не запускать боевую копию: старый узел может продолжать рассылки,
   задания, приём заказов и работу со складом. DNS сам по себе их не останавливает.
2. Если старый сервер доступен: остановить запись и PocketBase, получить финальную
   согласованную копию базы И файлов. При недоступности использовать проверенный
   snapshot, зафиксировать окно потери данных и сверить его с МойСклад/банком.
3. Разместить бинарник ИМЕННО сохранённой версии, hooks/migrations/site из того же
   snapshot, восстановленные pb_data, системную службу и необходимые ключи среды.
   Проверить абсолютные пути, права `venikoff`, Caddy, firewall, автозапуск, свободный диск.
   Не применять текущие миграции к старой копии без отдельной проверки совместимости.
4. Сверить последние заказы, invoice, статусы CloudPayments, кассовые чеки и
   идентификаторы МойСклад; не импортировать заказы вслепую. Старая копия может
   повторить уведомления, задания, чеки/возвраты. Перед запуском разобрать очередь
   с учётом уже выполненных операций; продумать разрыв нумерации после snapshot.
5. После изоляции старого узла: настроить TLS на новом (DNS challenge заранее либо
   выпуск сертификата после DNS), переключить A и имеющиеся AAAA всех витрин и www,
   запустить единственный активный PocketBase. Проверить маршруты Caddy:
   `/api/*`, SSR через `/api/page`, `X-Forwarded-Host`, закрытый `/_/`.
   Текущие `domain.sh` и `domains.sh` содержат IP старого узла: НЕ запускать без адаптации.
6. Проверить главную, каталог, админку, фото, обе витрины, склад, ботов и обратные
   вызовы платежей. Контрольную оплату проводить отдельно по согласованному сценарию.
   Проверить ограничения IP интеграций. Внешний мониторинг должен видеть новый узел.
7. Старый сервер после возвращения держать выключенным/изолированным до сверки.
   Обратный переход — новый перенос актуальных данных с нового активного узла,
   а не переключение DNS на старую базу.

## Хранение

Копии содержат персональные данные и секреты интеграций. Хранить в России,
шифровать restic; ограничить доступ. Не складывать ZIP в публичный репозиторий.
Сроки хранения и ограничение удаления в хранилище согласовать при настройке.
Экспорт ничего не удаляет: очистку старых snapshots и lifecycle настраивать
отдельно после успешного восстановления. Копии у того же провайдера не закрывают
сценарий полного отказа его панели/сети.

## Установка службы экспорта после проверки хранилища

Сначала прочитать ARCHITECTURE.md. Эти действия выполняются на основном сервере,
когда есть доступ к нему и готов независимый restic-репозиторий.

1. Установить restic, python3 и flock; проверить свободный диск и реальные пути.
2. Скопировать export-backup.sh и pb_backup.py в /opt/venikoff/recovery.
3. Создать /etc/venikoff с правами 0700. Перенести backup.env.example в
   /etc/venikoff/backup.env, заменить заполнители через защищённую настройку.
   Сохранить пароль restic в /etc/venikoff/restic-password. Оба файла: root, 0600.
4. Скопировать venikoff-backup.service и venikoff-backup.timer в /etc/systemd/system.
   Проверить их через systemd-analyze verify, выполнить systemctl daemon-reload.
5. Запустить systemctl start venikoff-backup.service. Проверить результат через
   systemctl status и journalctl -u venikoff-backup.service. Убедиться, что snapshot
   доступен из ДРУГОЙ среды, и провести восстановление.
6. Только затем включить systemctl enable --now venikoff-backup.timer.
   Расписание: каждый час на 20-й минуте UTC плюс задержка до двух минут.
   Это частота ЭКСПОРТА, а не создания ZIP. Повторная выгрузка дневного ZIP не
   уменьшает возможную потерю данных.
7. Проверить systemctl list-timers venikoff-backup.timer и настроить независимые
   сигналы о неуспехе службы и отсутствии свежих snapshots. Пока сигналы не
   проверены, потеря копирования может остаться незаметной.

Служба не устанавливает зависимости, не создаёт хранилище и не меняет частоту
штатных копий PocketBase. Шаблоны службы не испытаны на боевом сервере.
